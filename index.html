Internet as Strategic Terrain: build plan

Detect the disruption, reconstruct the event, assess the evidence, then explain the possible causes. v1.0 ships at Day 90; the command-center console (v2.0) follows at Day 107. Three tasks a day, about 30 to 60 minutes in total, with a buffer day closing every phase. Progress saves in this browser.

About this project

Internet as Strategic Terrain treats the internet as a place where events leave measurable traces. When a region goes dark or its traffic is rerouted, several independent sources record it: active probing, BGP routing tables, and censorship measurements. This project builds a complete, reproducible pipeline that pulls those sources together and tests, with confidence intervals, how much combining them improves on each one alone.

The question

Can independent measurement sources be combined to detect, reconstruct and characterise connectivity disruptions more reliably than any single source?

First case

The Kherson outage and rerouting of 30 May 2022, checked against published reports from Cloudflare, WIRED and others. If historical coverage is too thin, the fallback is Egypt or Libya in 2011, the events studied in the Dainotti et al. baseline paper.

What you will have at the end

  • Raw IODA, RIPE, RouteViews and OONI data, downloaded repeatably with checksums, API versions and a response cache
  • One DuckDB over Parquet store with schema contracts, quality tests and freshness monitoring
  • A scheduled incremental job, so ingestion runs on its own and not only by hand
  • One disruption rebuilt from real observations on a single timeline, with start and end as ranges
  • A Streamlit dashboard: map, synchronised timeline, AS path graph and evidence panel
  • A pre-registered evaluation on 8 to 10 events plus 20 or more quiet windows, with bootstrap confidence intervals, an ablation, and the IODA and Cloudflare Radar alerts as benchmarks
  • A research report, README, architecture diagram, CI from day 2, a live demo and a v1.0 release
  • Then, as v2.0: a command-center console modelled on the target image below, with metric cards, recent events, an impact timeline with latency and traffic tabs, an AS path panel, and an evidence and confidence panel

Ground rules

  • Detect the disruption, reconstruct it, assess the evidence, and only then consider causes.
  • An outage alone does not prove an attack, censorship or intent.
  • Missing data is not negative evidence.
  • A change in the number of visible BGP peers is not a route change. Normalise by peer count.
  • Never overwrite raw data. Every finding links back to its source records.
  • Write the hypotheses, event-selection rules and train/test split before running any detector.
  • Free public data and open-source tools only.
  • Explanations are labelled Plausible, Possible or Unlikely and linked to evidence. They never get percentages, because nothing here is a calibrated probability model.
  • Sources added after the Day 75 freeze are exploratory and stay out of the pre-registered evaluation.

How to use this page

107 days, three tasks a day, about 30 to 60 minutes a day, across eight phases: v1.0 is complete at Day 90 and stands on its own, and Days 91 to 107 are an optional console extension. Each phase ends with a buffer and gate day: use it for anything that slipped, then run the gate checks. Every task has its own reading, data or tool links underneath it. Tick tasks off as you go; progress saves in this browser. Short on time? Do one task, and let the buffer day absorb the rest.

Phases and gates
If you fall behind

Every phase ends with a buffer day. If you are more than two days behind at a gate, cut in this order and write the cut into the README:

  1. Go from 10 events to 8, keeping Egypt, Libya and Kherson.
  2. Use make plus cron instead of Prefect.
  3. Drop the RouteViews cross-check (Day 50) and keep the single-vantage caveat.
  4. Simplify the AS graph view to a table of before and after paths.
  5. Replace the demo video with annotated screenshots.

Never cut: the manifest and checksums, the frozen test split, peer-count normalisation, CI, or the limits section.

The console extension (Days 91 to 107) is optional because v1.0 stands on its own. If you fall behind there, cut in this order:

  1. The cable layer and infrastructure card (Day 96).
  2. The GDELT context cards (Day 97).
  3. The users-impacted metric and APNIC (Day 95).
  4. The Traffic tab (Day 94).

Never cut: the confidence rubric, the no-percentages rule, or the warning box.

  • One disruption rebuilt from real observations, with start and end as ranges
  • Connectivity and routing views share one timeline, normalised by peer count
  • Hypotheses, event rules and the tuning/test split committed before the detector ran
  • Baseline, single-signal and multi-signal detectors evaluated on 8 to 10 events plus quiet windows, with bootstrap confidence intervals and benchmarks against IODA and Cloudflare Radar
  • Missing data, false positives, vantage-point bias and ASN-to-region caveats documented
  • Automated tests and CI running since Day 2, with a coverage threshold

Stack

Python, httpx, DuckDB (with spatial extension) over Parquet, RIPE Atlas and APNIC data for v2, GeoPandas, NetworkX, Plotly, Streamlit, pandera and Pydantic, Prefect (or make plus cron), pytest and Hypothesis, uv, Docker Compose, GitHub Actions. What changed to earn each score
  1. Research design. Day 9 writes hypotheses with measurable success criteria and event-selection rules before any result is seen. An ablation compares each source alone with the combination, and IODA alerts and Cloudflare Radar events act as independent baselines. Events and start/end times carry uncertainty ranges.
  2. Reproducibility and provenance. A uv lockfile pins dependencies, every raw API response is cached, and the manifest records SHA-256, source ID, retrieval time, API version and git commit. Day 25 re-runs everything from an empty cache, and Day 85 repeats it on a clean container.
  3. Portfolio and communication value. A live Streamlit deployment, a 3-minute demo, a case-study post, release notes, a CITATION file and a research report with confidence intervals. The README documents what was cut and why.
  4. Data engineering breadth. Schema contracts that fail on drift, freshness, row-count and null-rate monitoring, an idempotent last-24-hours job on a Prefect schedule, a second BGP vantage set, and one analytic store (DuckDB over Parquet with spatial queries) instead of two.
  5. Evaluation rigour. 8 to 10 events and 20 or more matched quiet windows, labels with confidence and a second labelling pass, a split frozen and tagged before detectors run, bootstrap confidence intervals, a threshold sensitivity sweep, a leakage check and a single test-set run.
  6. Test and CI timing. The first pytest and GitHub Actions run land on Day 2. Nearly every ingestion and storage day ends with a quality test, so bugs surface the day they are written.
  7. Schedule realism. Time is stated honestly as 30 to 60 minutes a day, MRT parsing and the detectors are split across more days, the dashboard shrinks from 12 days to 11 with a buffer, and a buffer day ends every phase. A written cut order covers the case where you fall behind.
Biases and risks the plan now handles
  1. BGP vantage-point bias. Days 45 to 49 normalise by active peer count, exclude periods where the peer set changed, and cross-check against RouteViews.
  2. ASN-to-region geolocation. network_entities stores a geolocation_confidence field, the map tooltips show it, and the report states the caveat.
  3. External dependency risk. Terms and API limits are checked on Day 8, API versions go into the manifest, and cached raw responses let you work offline if an API changes.
  4. Over-claiming causes. The target console shows explanation percentages. The plan replaces them with Plausible, Possible and Unlikely labels, each linked to evidence, and keeps the warning box.
  5. Data-quality versus presentation balance. Monitoring and schema contracts take 3 of the first 40 days, against 11 days for the dashboard.
Risks that remain
  1. Data coverage is unproven. Kherson coverage in IODA, RIS and OONI is untested until Days 5 to 7. The Day 10 gate and the Egypt and Libya fallback are the safeguard.
  2. Small event count. Even 10 events give wide intervals. The report should say so rather than over-claim.
  3. Label quality. Ground truth comes from published timelines, which can be imprecise. Confidence on each label and a second labelling pass reduce this but cannot remove it.
  4. Console scope. Matching the target means about five new sources. Two are optional (cables, GDELT), and all are exploratory because they arrive after the evaluation freeze. v1.0 stands on its own if v2.0 slips.
  5. Latency and user-estimate coverage. RIPE Atlas probes may be sparse near a given event, and APNIC estimates are unvalidated. Both show as ranges or No data, not as findings.
  6. Execution. A plan scored 10 on paper still depends on keeping to it. Use the buffer days and the cut order.
